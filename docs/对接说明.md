# 对接说明（DSH 引擎）

本文件维护本插件与官方 DeepSeek Harness（dsh）之间的对接进度：每轮官方发版后重新盘点一次，
更新下面的四类差异表与验证边界。Command Code CLI 侧的对接见
[模型与上游同步](agent-reference/model-catalog.md)与 `dsh-commandcode-upstream` 技能。

## 二、四类差异对照

| 类别 | 内容 |
| --- | --- |
| 双方都有 | 消息与内容块、结构化错误、凭据解析、易变设置、图片卸载、严格远端编解码、五个客户端插槽、会话费用投影、逻辑历史读取与精确分支边界、`addition-only`（仅新增）工具声明、`imageRequestTarget`（图片请求目标） |
| 上游有、我方未接 | `systemPromptUpdate: 'in-history'`（历史内系统提示替换）、原生工具延迟激活语义、`prepareCall` 可选准备回调、Typert 严格投影（`input({strict:true})` 与 JSON Schema）、插件市场（plugin-market 五个新包，默认关闭）、Host 发布版本一致性闸门（仅影响开发态热更新，见第 9 条） |

| 双方都没有 | 配置与凭据的跨服务原子事务、对在途请求追溯改写配置 |

差异细节：

1. **破坏性变化（唯一一处）：兼容性判定改为只读 `engines.dsh`。**官方在本次发布中才补上说明文档
   （`docs/upgrade-guide/v0.2.1-alpha.3/plugin-engines-dsh/guide.zh.md`），讲的是上一版就已生效的规则：
   `app-boot/src/plugin-compatibility.ts` 的 `unmetRequirements` 先看 `engines.dsh`，**只要该字段存在就只按它
   判定、完全忽略 `@deepseek-ai/dsh*` peer**，只有缺少该字段时才回落到 peer 规则。判定不通过有三条后果：
   插件行被 preflight 禁用（`compatibility-preflight.ts`）、作为 profile bundle 被**静默跳过**
   （`profile.ts` 的 `skippedBundles`，只在 stderr 打一行，用户看到的是 provider 突然消失）、
   以及 `dsh plugin add` 在 pnpm 之前就拒绝（`plugin-manager/src/operations.ts`，`pnpm view` 现在也查 `engines`）。
   插件旧声明 `0.2.0-rc.2 || 0.2.1-alpha.3` 不含 alpha.4，已同批替换为 `0.2.0-rc.2 || 0.2.1-alpha.4`，
   见第五章第 1 条。上游同批把拒绝记录 `IncompatiblePlugin`／`PluginCompatibility` 的 `peers` 字段更名为
   `requirements`（按 engines 规则判时键为 `engines.dsh`）；插件不读这两个结构，只需同步文档。
2. **直接依赖的 14 个上游包源码零变化**：`dsh-llm`、`dsh-settings`、`dsh-credentials`、`dsh-commands`、
   `dsh-typert-protocol`、`dsh-web`、`dsh-attachment`、`dsh-timeout`、`dsh-launch-environment`、
   `dsh-client-locale`、`dsh-client-ui-renderer`、`dsh-client-ui-settings`、`dsh-client-ui-slots` 等在两版之间
   **只有版本号一行差异**，`dependencies`／`peerDependencies`／`peerDependenciesMeta`／`engines`／`dsh` 块
   逐字节相同 —— 无新增必装 peer、无移除 peer、无范围语义变化。
3. **`@deepseek-ai/dsh-api-remotes` 的源码变化是纯增量**：新增 plugin-market 远端贡献与
   `plugin-market/changed` 事件转发，既有命名空间（`remote.settings`、`remote.credentials`、
   `remote.commandcode`）未动。该包新增的 `@deepseek-ai/dsh-plugin-market` 导入是 devDependency，
   发布产物里已被内联（`lib/client.js` 零静态 import），**不会**造成 ESM 链接期失败，也**不会**被自动安装
   ——profile 的 pnpm 写死 `autoInstallPeers: false`，不存在 peer 自动兜底。
4. **Web 静态种子表零变化**：`packages/client/web/src/seed.ts` 与 `platform.ts` 两版逐字节相同，
   `lib/client.js` 的三个 `require()` 目标（`react`、`react/jsx-runtime`、
   `@deepseek-ai/dsh-client-ui-primitives`）仍然可解析。核对时顺手修正了
   [引擎兼容](agent-reference/engine-compatibility.md)里种子表清单漏列 `zod` 与 `@tanstack/react-virtual`
   的既有缺陷（该二项在 alpha.3 就已预置，属文档遗漏而非本轮变化）。
5. **五个在用插槽的契约零变化**：`settings.section`、`settings.models.provider-card`、`sidebar.footer.action`、
   `main`、`conversation.composer.dock` 的名字、kind、owner props 与 outlet 渲染调用逐字未变；
   `ui-slots` 的 `src/` 零差异。卡片依赖的 DOM 耦合（`data-slot` 属性 + 相邻兄弟 CSS module 类名含 `editor`）
   仍然成立：`.editor` 类保留，`renderSlot(...)` 三处调用参数与 DOM 顺序均未变。
6. **`ui-conversation` 的编辑器契约有实质改写**（`InputEvent`、`CommandClaim`、`InputTarget`、新增
   `resolveClaim`），但那是编辑器内部契约，插件只往 composer dock 注册一个展示条目，**零引用**这些类型。
7. **`ui-settings-models` 新增逐模型 `reasoningEfforts` 编辑界面**：宿主卡片与 `CustomProviderCard` 多了
   `reasoningLevels` 属性，其来源是 `reasoningLevelChoices(piAi, schema)` —— 只读 **`llm-pi-ai` 命名空间
   自己的 Config schema**，与第三方 provider 卡片的插槽契约无关。插件自己的推理档位数据
   （`src/capabilities.ts` 的 `KNOWN_EFFORTS`）若要露出同款控件，需在插件自己的卡片里实现，属独立功能，
   本轮不做。
8. **Cordis 与 Schemastery 配对未变**：alpha.4 仍配 `~4.0.5-alpha.2` 与 `~3.18.5-alpha.2`，与 alpha.3 相同，
   npm 没有为它们发 `dsh-0-2-1-alpha-4` 标签；既有声明范围 `~4.0.5-alpha.1` / `~3.18.5-alpha.1` 已覆盖，
   两个范围**不动**。
9. **新增但默认关闭**：alpha.4 引入 5 个插件市场相关包（`dsh-plugin-market`、`dsh-plugin-market-index`、
   `dsh-client-ui-plugin-market`、`dsh-experimental-plugin-market-bundle`、`dsh-plugin-market-generator`），
   其中 `dsh-plugin-market-generator` 是 `private` 未发布；市场服务与 Discover 页属 `OPTIONAL_BUNDLES`，
   默认关闭，默认启用的 `dsh-plugin-market/tools` 行有 `ctx.inject(['pluginMarket'], …)` 保护。
   客户端另有 Host 发布版本一致性闸门（`ReleaseChangeGate`）：页面只应用与自身 boot release 相同的模块图，
   版本不一致时暂停插件热更新并提示刷新 —— 只影响开发态，不改变插件契约。
10. **未变的其他面**：`RequestMessage`、`GenerateOptions`、`ContentBlock`、`LlmError` 与模型能力类型
    （`packages/llm/*/src`）零变化；`toolUpdate: 'addition-only'` 在新引擎的真实工具历史检查中通过；
    审批 seam 仍然完全不接入（`src/` 无 `approval`／`pre-execute` 引用），上游相关包只有版本号变化。

## 四、验证证据与边界

1. **真实引擎矩阵**：`npm run test:engine` 对每个已声明引擎各跑一遍 —— 发布入口加载、静态具名导入审计、
   客户端 `require()` 种子审计、**宿主准入判定**、易变设置契约、持久化图片卸载契约、账号开通观察流取消、
   三协议 22 个流终态场景、网关切换期间的请求快照隔离、真实历史服务读取关闭会话与分支、严格分析远端校验。
   当前两个引擎（`0.2.0-rc.2`、`0.2.1-alpha.4`）全部通过（`engine-load smoke passed on all 2
   declared-compatible engines`）。**准入判定是本轮新增的一项**：此前脚本的每条检查都走「把发布面装进引擎
   的 peer 树再加载」，看不见宿主准入判定本身，所以 alpha.4 上会出现「脚本全绿、真实安装被拒」。红绿对照
   已实测：alpha.4 通过，`--version 0.2.1-alpha.3`（已退出兼容范围）被拒并逐条报出未满足项；旧引擎走 peer
   规则、新引擎走 `engines.dsh`，两种判据都被覆盖。
2. **逐引擎隔离安装**：`npm run test:install` 为每个已声明版本各建一个全新的 pnpm 10.34.5 generation，
   安装时把该版本的必需 Harness peer 一起钉死，再断言锁文件解析出的 `@deepseek-ai/dsh-llm` 恰好是目标版本。
   当前两个版本全部通过（`engine matrix verified: 0.2.0-rc.2, 0.2.1-alpha.4`）。
3. **类型与测试**：在**升级后的 alpha.4 开发依赖**下运行 `npm run typecheck` 与全量 987 项测试，均通过；
   `npm run build` 产出两段构建。
4. **静态具名导入**：以真实 alpha.4 引擎逐条核对 `lib/index.js` 的静态具名导入，全部存在 —— 具名导入缺失
   是 ESM（ECMAScript 模块）链接期致命错误，必须单独证明。
5. **锁文件同步性**：按[《决策记录》第八章第 11 条](决策记录.md#八dsh-引擎兼容范围与验证边界)在隔离目录用
   当前 `package.json` + `package-lock.json` 跑 `npm ci --dry-run` 通过（100 个包全部解析为 alpha.4，平台
   可选依赖分支 10 个保持完整）。本轮**没有**重新解析锁文件：隔离重新解析会把 `@rolldown/binding-*` 等
   21 个无关依赖顺带升级，改为只替换 29 个 `@deepseek-ai/dsh*` 条目与根声明面，非 dsh 条目逐字节不变。
6. **未覆盖**：浏览器实际渲染、真实账号与付费请求、凭据持久化、跨平台运行、长期运行稳定性，以及 headless
   下「导出环境变量后能正常发请求」的端到端表现，都需要实际环境验收，不能由本地绿色检查推定。客户端插槽与
   DOM 耦合（`data-slot` 锚点、相邻 `editor` 类）本轮只做了源码级逐字节核对，未在真实浏览器里跑一遍渲染。
   另有一处**裁剪 shell 风险**：`ui-settings-general` 在 alpha.4 新增了必填注入 `modules`，标准 Web 引导会
   提供，但自行裁剪装配的 shell 若不提供，`settings.section` 声明不激活，插件的设置页会静默不挂载。
7. **本地环境残留（非插件缺陷）**：本机 web profile（`~/.dsh/profiles/web/cordis.patch.yml`）里
   `llm-deepseek-account` 条目的 `models: []` 属 alpha.3 那轮记录的旧值残留，按维护者决定暂不清理，因此本地
   启动会持续打印一条「1 entry did not activate」警告。该条目是上游账号 provider，失败为可选条目失败，
   commandcode 路由与其它条目的激活不受影响；此项未纳入自动化验证，也不构成插件缺陷。

## 五、本轮改动

1. **引擎声明替换**：`@deepseek-ai/dsh-*` peer 析取、`dsh.compatibility.dsh`、`engines.dsh`、
   `dsh.compatibility.dshReleases`、`devDependencies` 与 `package-lock.json` 同批由 `0.2.1-alpha.3` 替换为
   `0.2.1-alpha.4`（`package.json` 共 37 处版本串），版本号升至 `0.13.4`；`@deepseek-ai/cordis` 与
   `@deepseek-ai/schemastery` 的范围**不变** —— alpha.4 配对的仍是 `4.0.5-alpha.2` 与 `3.18.5-alpha.2`，
   与 alpha.3 相同。
2. **锁文件精准更新**：隔离重新解析会把 21 个无关依赖（`@rolldown/binding-*`、`@oxc-project/types` 等）
   顺带升级，违反[《决策记录》第八章第 11 条](决策记录.md#八dsh-引擎兼容范围与验证边界)的约束，因此改为只
   替换 29 个 `@deepseek-ai/dsh*` 条目及其根声明面：非 dsh 条目逐字节不变、条目零增删、平台可选依赖分支
   保持 10 个。
3. **验证盲区补口**（`scripts/verify-engine-load.mjs`）：新增 `checkEngineAdmission(engineRoot, version)`，
   用该引擎自己的 `evaluatePluginCompatibility` 对发布清单求值；函数或包缺失时只记警告，不把「引擎没提供」
   读成「插件不兼容」。调用位置在静态具名导入审计之后、客户端 `require()` 审计之前。
4. **测试注释修正**：`tests/package.test.ts` 中原写「`compatibility.dsh` 与 `engines.dsh` 都只是声明面、
   dsh 自己不读」，自 alpha.4 起不再成立，已改写为「`engines.dsh` 是宿主唯一判据」并写明判定不通过的三条后果。
5. **文档同步**：本文件、[引擎兼容](agent-reference/engine-compatibility.md)（兼容范围、种子表清单、
   `test:engine` 说明与第三节新增 alpha.4 轮次）、[决策记录](决策记录.md)第八章第 12 条、`CHANGELOG.md`、
   两份 README、[仓库地图](agent-reference/repository-map.md)、[账号与重试](agent-reference/accounts-and-retry.md)、
   [客户端与设置](agent-reference/client-and-settings.md)、[模型成本与性能分析](模型成本与性能分析.md)。
   顺带修正两处既有文档缺陷：种子表清单漏列 `zod` 与 `@tanstack/react-virtual`（该二项在 alpha.3 就已预置）。
6. **刻意不做**：插件市场五个新包不接入（属可选 bundle、默认关闭）；逐模型 `reasoningEfforts` 编辑界面不接入
   （其等级来源是 `llm-pi-ai` 命名空间自己的 Config schema，与第三方 provider 卡片插槽无关）；客户端 Host 发布
   版本一致性闸门不需要插件配合。插件 `src/` 与 `lib/` 运行时零改动，测试夹具也零改动。
