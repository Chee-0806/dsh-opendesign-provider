本文件维护本插件与官方 DeepSeek Harness（dsh）之间的对接进度；每轮官方发版后重新盘点四类差异与验证边界。Command Code CLI（命令行工具）侧见[模型与上游同步](agent-reference/model-catalog.md)。

## 二、四类差异对照

| 类别 | 内容 |
| --- | --- |
| 双方都有 | 消息与内容块、结构化错误、凭据解析、易变设置、图片卸载与请求目标、严格远端编解码、五个既用客户端插槽、会话费用投影、历史读取与精确分支边界、`addition-only`（仅新增）工具声明 |
| 上游有、我方未接 | rc.2 首发的官方网页搜索／抓取后端 `@deepseek-ai/dsh-web-deepseek-api`（宿主包，组合层行 id `web-deepseek-api`，向 `ctx.web` 注册 `deepseek-search-api` 搜索提供方与一个抓取提供方）；官方模型标签插槽 `conversation.input.model.label`（`single`，单占类，已由 `dsh-client-ui-deepseek-model-label-1017` 占用）；既有的历史内系统提示替换、原生工具延迟激活、`prepareCall`（调用准备）与插件市场仍不接入 |
| 我方有、上游没有专用契约 | Command Code 账号轮换与网关探测、三协议转换、网关能力与价格、历史模型成本分析与固定工作量试算、版本与零数据保留请求头、压缩摘要成本对账字段 `summaryTokens`、网页搜索的运行时选择开关（`webSearch`） |
| 双方都没有 | 配置与凭据的跨服务原子事务、对在途请求追溯改写配置 |

1. **支持矩阵为两个 RC 引擎。**`dsh.compatibility.dshReleases` 两条记录 `{"0.2.0-rc.2": "compatible", "0.2.1-rc.2": "compatible"}`，`dsh.compatibility.dsh`、`engines.dsh` 与 15 个 peer／19 个开发依赖的 `@deepseek-ai/dsh-*` 都是裸版本析取式 `0.2.0-rc.2 || 0.2.1-rc.2`；`tests/package.test.ts` 断言恰好两条且逐字等于这两个版本。宿主判定语义**未变**（自 `0.2.1-alpha.4` 起只读 `engines.dsh`，`semver.satisfies` 带 `includePrerelease: true`）：`0.2.0-rc.2` 上仍按 dsh 对等依赖范围判定，因此两处声明必须同批同步。反转决策、判据与影响见[《决策记录》第八章第14条](决策记录.md#八dsh-引擎兼容范围与验证边界)；rc.2 轮次的单引擎收敛见同章第13条（其 (a) 已被第14条替代）。
2. **Cordis 与 Schemastery 写成按引擎配对的析取式。**rc.2 是本批次第一个携带正式版配对的引擎（`cordis 4.0.5`、`schemastery 3.18.5`，两者皆为 npm `latest`；npm 上没有 `dsh-0-2-1-rc-*` 预发布标签）。**两代引擎的配对不同**：npm 实测 `0.2.0-rc.2` 的包 peer `cordis ~4.0.4`、依赖 `schemastery ~3.18.4`，`0.2.1-rc.2` 配对 `~4.0.5`／`~3.18.5`，因此按仓库「多引擎并存写析取式」规则声明为 `~4.0.4 || ~4.0.5`／`~3.18.4 || ~3.18.5`——单分支 `~4.0.5`／`~3.18.5` 只适用于 rc.2 轮次的单引擎矩阵，它解析不到旧引擎的配对，会在 profile 里解析出冲突副本。析取式同时覆盖两代，并排除 `4.0.5-alpha.2` 这类 `-alpha` 预发布；这两个名字不匹配 `@deepseek-ai/dsh*` 前缀、宿主准入不读它们，差异只在 pnpm 解析层生效。写法规则见[引擎兼容](agent-reference/engine-compatibility.md)。
3. **唯一运行代码破坏点：网页能力缝的选择契约。**`WebRuntimeConfig.searchProvider`／`fetchProvider` 由「构造时读一次的普通字段」改为 `Volatile`（易变引用，每次调用读一次），构造函数 `config` 由可选变必填，插件此前直写的私有实例字段 `searchProviderId`／`fetchProviderId` **被整体删除**。旧实现因此在 rc.2 上变成「写到一个没有读取方的属性」——不抛错、功能静默失效。本轮改按 rc.2 官方易变写入路径修复：写入 profile 的易变字段，由 loader 原地提交进运行中的引用，**不重挂载** `web` 条目；pre-rc.2 引擎（含 `0.2.0-rc.2`）没有该引用也没有 `web` 设置行，那里选择仍是实例自有字段 `searchProviderId`（仅内存、随实例失效），插件按每次观察到的形状分派，一个构建同时服务两个引擎。所有权策略是**不夺取用户层已有的他人显式选择**：官方「网页搜索」设置已 pin 其他后端时，插件让 `commandcode` 保持已注册但未被选中并报出该状态（开关提示文案 + 一行宿主日志），只在无人 pin 时才接管；旧引擎没有这一设置面，因此看不到他人的 pin。适配细节与冲突场景见[账号与重试](agent-reference/accounts-and-retry.md)的网页搜索段与 `web-seam.md`；选择策略、被否替代项与旧引擎形状见[《决策记录》第八章第13条 (b)、第14条 (b)](决策记录.md#八dsh-引擎兼容范围与验证边界)。
4. **其余 16 个直接依赖包与 9 个 vendor 包源码零差异。**逐个执行 `diff -rq` 确认：除 `@deepseek-ai/dsh-web` 外，插件消费的包在 rc.2 与 `0.2.0-rc.2` 之间只有版本串、新增 `locale/` 目录与注释级改动；`vendor/cordis` 4.0.4 → 4.0.5、`vendor/schemastery` 3.18.4 → 3.18.5 的逐文件 diff **仅差版本行**，`vendor/loader`（`loader/volatile-update` 契约）只差 2 处热更新记录。逐包结论与证据见 `host-api.md`。
5. **exports 漂移全部未踩。**7 个包（`dsh-agent`、`dsh-client-ui-renderer`、`dsh-commands`、`dsh-credentials`、`dsh-llm`、`dsh-scope`、`dsh-session`）新增 `./locale/*.json` 并删除 `./invariant`；`dsh-typert-protocol` 新增 `./remote-info`。插件源码只引用四个 `/client` 子路径（`dsh-api-remotes`、`dsh-client-locale`、`dsh-client-ui-renderer`、`dsh-client-ui-settings`），四个子路径全部保留；被删的 `./invariant` 在插件源码、测试与脚本中零命中。
6. **rc.2 首发两个官方包，与插件无冲突，且带来一条硬约束。**`@deepseek-ai/dsh-web-deepseek-api` 注册的搜索提供方 id 是 `deepseek-search-api`，与插件的 `commandcode` 不同（`registerSearchProvider` 只在 id 重复时抛 `WEB_DUPLICATE_PROVIDER`）；宿主行 id `web-deepseek-api` 与插件的 `llm-commandcode` 也不同。`@deepseek-ai/dsh-client-ui-deepseek-model-label-1017` 占用的 `conversation.input.model.label` 是 **`single`（单占）类插槽，同优先级重复注册会直接抛错**，插件不得为该插槽注册任何贡献。插件五个既用插槽（`settings.section`、`settings.models.provider-card`、`main`、`sidebar.footer.action`、`conversation.composer.dock`）的声明文件与 `0.2.1-alpha.5` 逐字相同，占用者与本插件 id／key 均不冲突。
7. **打包与客户端面未变。**Web 预置模块表（`packages/client/web/src/{seed,platform}.ts`）逐字相同，`lib/client.js` 的三个 `require()` 目标（`react`、`react/jsx-runtime`、`@deepseek-ai/dsh-client-ui-primitives`）仍全在表内；`dsh.client.inject` 的三个包名在 rc.2 花名册中仍存在，语义仍是「boot 图前置依赖」而非服务注入列表；`dsh.client.platform`、`exports["./client"]`、`dsh.bundle.patch` 的解析契约均未变。既有的「optional peer 必须同时是 devDependency」三件套仍然成立。
